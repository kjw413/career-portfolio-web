# 김종우 포트폴리오 리디자인 설계서

**작성일:** 2026-08-16
**대상 저장소:** `kjw413/career-portfolio-web`
**배포 주소:** `https://kjw413.github.io/career-portfolio-web/`
**범위:** 디자인·콘텐츠 구조·GitHub 자동 동기화·GitHub Pages 배포 설계. 이 문서는 구현을 포함하지 않는다.

## 1. 목표

포트폴리오의 첫 화면만 보고도 방문자가 다음 세 가지를 이해하게 한다.

1. 김종우는 전자전기공학을 기반으로 제조 현장, 데이터·AI, 임베디드 시스템을 연결하는 **시스템 문제 해결형 엔지니어**다.
2. 프로젝트를 단순히 수행한 것이 아니라 반복 업무 시간, 예측 오차, 적용 범위처럼 확인 가능한 성과를 만들었다.
3. 채용담당자는 짧게 훑을 수 있고, 기술 면접관은 클릭을 통해 문제 해결 과정과 기술 세부사항을 확인할 수 있다.

특정 회사나 직무명에 맞춘 자기소개보다 여러 직무에서 통용되는 문제 해결 방식과 증거를 전면에 둔다. 제조·데이터/AI·임베디드 경험은 별개 경력이 아니라 하나의 시스템 관점이 적용된 세 영역으로 설명한다.

## 2. 선택한 방향

검토한 세 가지 첫 화면 구조 중 **C안: 균형형 프로필 대시보드**를 채택한다.

- 왼쪽: 4:5 비율 비즈니스 프로필 사진, 이름, 전공, 현재 역할
- 오른쪽: 정체성 문장, 간결한 소개, 핵심 성과, 주요 이동 버튼
- 대표 문구: `시스템 문제 해결형 엔지니어`
- 세부 태그: `MANUFACTURING`, `DATA · AI`, `EMBEDDED · SYSTEM`, `AUTOMATION`
- 주요 버튼: `대표 프로젝트`, `이력서`, `GitHub`

사진 또는 이력서 파일이 없는 동안에는 깨진 이미지나 `추후 추가` 문구를 보여주지 않는다. 사진은 이니셜 플레이스홀더로 대체하고, 이력서 버튼은 파일 경로가 설정될 때만 노출한다.

## 3. 정보 구조

메인 페이지의 섹션 순서는 다음과 같다.

1. **Hero** — 사진, 이름, 정체성, 소개, 3개 CTA, 대표 수치
2. **Selected Impact** — 가장 강한 성과 3건을 상황·행동·결과로 요약
3. **Featured Projects** — BEMS, RPA, 텔레칩스 중심 사례
4. **Experience Timeline** — 빙그레, AI Elite, 텔레칩스, 인바디 등 전체 경험
5. **Capability Map** — 제조, 데이터·AI, 임베디드·제어, 자동화 역량
6. **Project Archive** — GitHub 공개 저장소 전체와 수동 프로젝트를 통합한 목록
7. **Education & Foundation** — 전공, 교육, 자격, 언어
8. **Contact** — 이메일, GitHub, 이력서

기존 페이지의 `Selected Work`와 `Project Archive`는 역할을 명확히 나눈다. 전자는 문제 해결 사례 3~4개만 보여주고, 후자는 누락 없는 전체 목록과 필터를 제공한다. 기존 `Field Engineering` 내용은 별도 장문 섹션으로 유지하지 않고 Selected Impact, Experience, Capability Map에 분산하여 중복과 페이지 길이를 줄인다.

## 4. 콘텐츠 모델

### 4.1 대표 성과

성과는 단위와 기준을 함께 표시한다.

| 표시 값 | 설명 | 표기 규칙 |
|---|---|---|
| `40분 → 3분` | MIS 수집 업무 1회 처리시간 | `1회 작업시간`을 함께 표기 |
| `월 약 12.8시간` | 기존 연 154시간의 월 환산 절감시간 | 상세 화면에 `154 ÷ 12` 산식 기재 |
| `MAPE 7%` | 전사 에너지 예측 오차 | 데이터 범위 또는 검증 조건 병기 |
| `5개 공장` | 에너지·생산 데이터 통합 범위 | 적용 범위를 함께 설명 |

추가 수치가 입력되면 동일하게 `값 + 기준 기간 + 계산 근거`를 기록한다. 근거가 확인되지 않은 수치는 자동 생성하거나 추정하지 않는다.

### 4.2 통일된 경험 카드

모든 대표 성과·프로젝트·경력 항목은 다음 순서를 사용한다.

1. 문제 또는 상황
2. 본인의 역할
3. 수행한 행동과 기술적 판단
4. 결과와 검증 근거

카드의 닫힌 상태에는 기간, 소속/분야, 제목, 핵심 성과 한 줄만 표시한다. 펼친 상태에는 역할·행동·기술·성과를 3~5개 항목으로 보여준다. BEMS, RPA, 텔레칩스처럼 기술 설명 가치가 큰 프로젝트에는 별도 사례 페이지 링크를 추가한다.

### 4.3 프로젝트 상세 페이지

상세 사례는 다음 목차를 공통으로 사용한다.

1. 문제 정의
2. 사용자와 현장 맥락
3. 제약 조건
4. 분석과 설계
5. 구현
6. 검증 결과
7. 본인의 역할
8. 배운 점과 다음 개선

회사 기밀이나 공개하기 어려운 절대 수치는 삭제하고 개선율, 시간 절감, 적용 범위, 본인의 의사결정으로 대체한다.

## 5. 상호작용

- 대표 성과와 경험은 카드 자체가 아니라 명시적인 펼침 버튼으로 열고 닫는다.
- 버튼에는 `aria-expanded`와 연결 대상 ID를 제공한다.
- 키보드만으로 모든 상세 내용을 열고 닫을 수 있어야 한다.
- 대표 프로젝트 카드는 상세 페이지로 이동한다.
- 아카이브는 `전체`, `제조·자동화`, `데이터·AI`, `임베디드`, `웹·도구` 필터를 제공한다.
- 필터 결과가 0건이면 빈 화면 대신 `해당 분야의 공개 프로젝트가 없습니다.`를 표시한다.
- 애니메이션은 진입 페이드, 테두리·그림자 변화, 펼침 전환으로 제한한다.
- `prefers-reduced-motion`에서는 이동과 자동 애니메이션을 제거한다.

## 6. 시각 디자인 시스템

### 6.1 색상

| 역할 | 색상 |
|---|---|
| 페이지 배경 | `#F8FAFC` |
| 카드 배경 | `#FFFFFF` |
| 본문·제목 | `#0F172A` |
| 핵심 강조 | `#2563EB` |
| 보조 강조 | `#38BDF8` |
| 구분선 | `#DCE5F0` |
| 보조 텍스트 | `#64748B` |

전자전기공학의 이미지는 회로나 전구 아이콘을 반복하는 방식이 아니라 정밀한 그리드, 얇은 선, 데이터 라벨, 명확한 수치 계층으로 표현한다.

### 6.2 타이포그래피와 카드

- 한글 본문은 시스템 산세리프를 우선하고 영문 라벨은 모노스페이스를 보조적으로 사용한다.
- 제목은 굵고 짧게, 설명은 닫힌 카드에서 최대 두 줄로 제한한다.
- 카드 모서리, 테두리, 내부 여백을 전 섹션에서 통일한다.
- 수치 성과는 문장보다 시각적으로 한 단계 크게 표시한다.
- 과도한 그라데이션, 유리 질감, 3D 그래픽은 사용하지 않는다.

### 6.3 프로필 사진

- 4:5 세로 비율의 비즈니스 프로필 사진을 사용한다.
- 원형 크롭 대신 모서리가 완만한 사각 프레임을 사용한다.
- 밝은 회색 또는 흰색 배경 사진을 권장한다.
- 최종 파일은 `public/profile.webp`로 저장하고 1배·2배 화면에서 선명하되 300KB 이하를 목표로 최적화한다.

## 7. 반응형 설계

- 데스크톱: Hero를 약 36:64의 사진/정보 2열로 배치한다.
- 태블릿: 사진 폭을 줄이고 성과 지표를 2열로 전환한다.
- 모바일: 사진 → 정체성 → 소개 → CTA → 성과 순으로 세로 배치한다.
- 모바일 CTA는 주 버튼을 한 줄 전체 폭으로, 보조 버튼을 2열로 배치한다.
- 아카이브 표는 모바일에서 기술 스택과 공개 상태를 보조 행으로 내려 가로 스크롤을 만들지 않는다.
- 360px 너비에서 텍스트 잘림, 겹침, 수평 스크롤이 없어야 한다.

## 8. 자동·수동 혼합형 콘텐츠 구조

### 8.1 자동 수집

GitHub API를 통해 `kjw413` 계정의 공개 저장소에서 다음 필드를 수집한다.

- 저장소 이름과 설명
- 저장소 URL
- 주요 언어
- Topics
- 최근 업데이트일
- Star 수
- archived 여부

수집 데이터는 `content/generated/github-repos.json`에 저장하며 페이지 렌더링 시 브라우저에서 GitHub API를 호출하지 않는다.

### 8.2 수동 작성

다음 정보는 GitHub 메타데이터로 판단할 수 없으므로 직접 관리한다.

- 프로필, 소개, 연락처, 사진, 이력서
- 경력, 교육, 자격
- 대표 성과와 계산 근거
- 대표 프로젝트 선정과 노출 순서
- 프로젝트의 한글 제목, 요약, 분야, 공개 여부
- 프로젝트 상세 사례의 본문

수동 데이터는 `content/profile.json`, `content/experience.json`, `content/project-overrides.json`, `content/projects/*.md`에 둔다. 동일 저장소의 자동 데이터와 수동 데이터가 충돌하면 수동 값을 우선한다. 프로젝트 연결 키는 저장소 이름인 `repoName`으로 통일한다.

## 9. 시스템 아키텍처

현재 기술 스택인 TypeScript, Next.js 16 App Router, React 19, Tailwind CSS 4를 유지한다. `next.config.ts`의 `output: "export"`, `basePath`, `trailingSlash`, `images.unoptimized` 설정도 유지한다.

```text
content/profile.json ─────────────┐
content/experience.json ──────────┤
content/project-overrides.json ───┼─ mergeProjects() ─ Next.js static export
content/projects/*.md ────────────┤                         │
GitHub API ─ sync-github.mjs ─ generated/github-repos.json ┘
                                                           │
                                   GitHub Actions ──────────┤
                                                           ▼
                                                GitHub Pages / CDN
```

GitHub Pages는 서버에서 Node.js를 계속 실행하지 않는다. GitHub Actions가 배포 시 HTML·CSS·JavaScript를 미리 생성하고, Pages가 정적 파일을 제공한다. 데이터베이스와 별도 백엔드 서버는 추가하지 않는다.

## 10. 동기화와 배포 정책

- 배포 트리거: `main` push, 수동 실행, 하루 1회 예약 실행
- 예약 실행 시 GitHub API 동기화 후 정적 빌드
- API 인증 정보는 Actions 환경에서만 사용하고 브라우저 번들에는 포함하지 않음
- API 호출 실패 시 기존 `github-repos.json`이 유효하면 캐시를 사용해 빌드 지속
- 캐시도 없거나 JSON 구조가 유효하지 않으면 빌드 실패
- 예약 실행에서 생성된 JSON은 배포 산출물에만 포함하고 자동 커밋하지 않음

이 방식은 사용자가 매번 저장소 목록을 수기로 고치지 않아도 최신 저장소를 반영하면서, 채용용 표현과 성과 문구는 직접 통제할 수 있게 한다.

## 11. 품질 기준

- `npm run lint`, `npm test`, `npm run build` 통과
- 360px, 768px, 1440px에서 레이아웃 검증
- 키보드만으로 CTA, 필터, 펼침 카드, 상세 페이지 이동 가능
- 색상 대비 WCAG AA 수준 확인
- 주요 이미지에 대체 텍스트 제공
- Lighthouse 기준 Performance, Accessibility, Best Practices, SEO 각 90 이상을 목표로 함
- GitHub API 실패 모의 테스트에서 기존 캐시로 정적 빌드 성공
- GitHub Pages의 `/career-portfolio-web/` 하위 경로에서 내부 링크와 이미지가 정상 동작

## 12. 콘텐츠 업데이트 절차

1. 사진 교체: `public/profile.webp` 교체 후 `content/profile.json`의 `photoSrc` 확인
2. 이력서 교체: `public/resume.pdf` 교체 후 `resumeHref` 설정
3. 경력 추가: `content/experience.json`에 항목 추가
4. 대표 성과 수정: `content/profile.json`의 metrics와 evidence 수정
5. 대표 프로젝트 변경: `content/project-overrides.json`의 `featured`, `order` 변경
6. 상세 사례 수정: 해당 `content/projects/<slug>.md` 편집
7. 저장소 기본 정보: GitHub에서 설명·Topics·언어를 수정하면 다음 예약 배포에 자동 반영
