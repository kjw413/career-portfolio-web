# 원장 기반 자기소개서 작성

## 왜 이 절차가 있나

2026 하반기 지원서 6건에 같은 예측 오차가 다섯 가지 값으로 적혀 있었습니다. 제출하고
나면 고칠 수 없습니다. 그래서 **기억으로 쓰지 않고 원장에서 인용**하고, 제출 전에
기계로 대조합니다.

## 절차

### 1. 입력 확인

회사, 직무, 문항 목록, 문항별 글자수, 제출 예정일. 빠진 것이 있으면 먼저 묻습니다.

### 2. 원장 읽기

`content/ledger/`를 직접 읽습니다. 저장소가 없으면
`https://kjw413.github.io/career-portfolio-web/ai/ledger.json`을 받습니다.

읽어야 할 것: `metrics.json`(수치), `phrases.json`(표현 규칙), `experiences/*.md`(경험
카드의 `canonical`·`forbidden`·`teamContext`), `selection-guide.json`(직무군),
`open-questions.json`(확인 필요), `facts.json`(학력·경력·자격).

### 3. 직무군 판정

`selection-guide.json`의 `job` 중에서 고릅니다. 목록에 없는 직무면 가장 가까운 것을
고르고 그 사실을 밝힙니다. 고른 직무군의 `primary`·`secondary`·`exclude`를 확인합니다.

### 4. 문항별 카드 배정 — **초안보다 먼저 보여 줍니다**

| 문항 | 배정한 경험 | 인용할 수치 | 고른 이유 |
|---|---|---|---|
| 1. … | `EXP-…` | `metric-id` | … |

한 문항에 카드 1~2개입니다. 셋 이상 넣으면 어느 것도 구체적이지 않게 됩니다.
`exclude`에 있는 카드는 쓰지 않습니다. 사용자가 배정을 고친 뒤에 초안을 씁니다.

### 5. 초안 쓰기

문항별 글쓰기 구조는 `anthropic-skills:cover-letter-writing` 스킬을 따릅니다.
이 스킬은 **무엇을 쓸 수 있는지**를 정하고, 그 스킬은 **어떻게 쓸지**를 정합니다.

원장이 정한 것:

- **수치는 `metrics.json`에서 가져옵니다.** 값과 함께 `condition`을 씁니다.
  `forecast-mape-all`은 "최근 6개월 기준 전 공장·전 에너지원 평균 MAPE 7.3%"이지,
  "예측 오차 7%"가 아닙니다.
- **레지스트리에 없는 수치는 쓰지 않습니다.** 필요하면 사용자에게 근거를 묻고
  `metrics.json`에 등록한 뒤 씁니다.
- **`status: 미확정`인 수치와 카드는 쓰지 않습니다.** 7번의 "확인 필요"로 돌립니다.
- **카드의 `canonical` 문장은 그대로 써도 됩니다.** 이미 사실 확인을 마친 문장입니다.
- **카드의 `forbidden`과 `phrases.forbidden`은 쓰지 않습니다.** 비슷한 뜻으로 바꿔
  쓰는 것도 안 됩니다. 금지한 것은 표현이 아니라 그 주장입니다.
- **팀 작업은 `teamContext`를 지킵니다.** 팀 결과물 전체를 개인 성과로 쓰거나 기여율을
  추정하지 않습니다.
- **재직기간·총경력은 제출일 기준으로 다시 계산합니다.** `facts.json`의 입사일에서
  계산하고, 과거 지원서의 값을 옮겨 적지 않습니다.
- 서로 다른 경험의 수치를 합산하거나 바꿔 쓰지 않습니다. BEMS의 월 4시간과 MIS RPA의
  일 40분은 다른 성과입니다.

### 6. 기계로 대조

```bash
npm run lint:claims -- --file 초안.txt --job "<직무군>" --date <제출일>
```

`고쳐야 할 것`이 하나라도 남으면 고친 뒤 다시 돌립니다. 통과하지 않은 초안을
최종본으로 내놓지 않습니다.

### 7. 결과물

세 가지를 함께 냅니다.

1. **본문** — 문항별 완성문
2. **근거표** — 문항 → 카드 ID → 수치 ID → 인용한 정본 표현
3. **확인 필요** — `open-questions.json`에서 걸린 항목과, 레지스트리에 없어 쓰지 못한 것

근거표가 있어야 사용자가 원장을 다시 열어 보지 않고도 검토할 수 있습니다.

### 8. 저장

- 자기소개서 본문은 **구글드라이브**에 둡니다: `<시즌>/<회사>_<직무>.txt`.
  hwpx로 제출하더라도 검사용 txt를 함께 둡니다.
- **저장소에는 본문을 넣지 않습니다.** `content/applications/index.json`에 시즌·직무군·
  제출일·드라이브 파일 ID·문항별 사용 카드·검사 결과만 추가합니다. 회사명도 넣지
  않습니다(이유는 `content/applications/README.md`).

## 대화 중 사실이 확정되면

사용자가 "그건 사실 이렇다"고 확정해 주면 **그 자리에서 원장을 고칩니다.** 나중으로
미루면 다음 지원서에서 같은 문제가 반복됩니다.

1. `content/ledger/`의 해당 파일 수정
2. `basis`와 `confirmedAt`에 근거와 날짜 기록
3. 옛 표기는 지우지 말고 `deprecated`에 추가
4. `npm run lint:ledger && npm test` 후 커밋

확정되지 않았으면 원장을 고치지 말고 `open-questions.json`에 질문을 추가합니다.

## 하지 않는 것

- 원장에 없는 경험이나 수치를 만들어 내지 않습니다
- 회사 홈페이지·뉴스에서 본 내용을 확인 없이 사실로 적지 않습니다
- 생년월일·주소·연락처·등록번호를 저장소에 남기지 않습니다 (드라이브 비공개 부록 사용)
- 법적 동의, 사실확인 서약, 최종 제출은 사용자가 직접 합니다
